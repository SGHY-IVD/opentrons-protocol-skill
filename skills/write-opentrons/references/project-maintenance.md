# 项目维护与发布

仅在修改、审查或发布技能项目时读取；不加入日常协议生成路径。协议审查见protocol-review.md，官方资料更新见upstream-maintenance.md，审查能力评估见assets/review-regression/maintenance.md。三者各自维护，本文件只组织项目生命周期。

## 每次修改的最小闭环

1. 先读当前文件与Git状态，明确本次问题、适用范围和是否改变生成行为；保留其他未提交工作。用户举例只用于理解意图，未明确普遍适用时不升格为全局规则。
2. 定位唯一规则出处：接口/安装、经验、数值或模板。先改权威条目，再检查受影响的入口路由、模板、审查项、回归答案和项目说明；只改有依赖的内容，不机械修改全部文件。
3. 按下表完成必要验证，记录实际覆盖与未覆盖项。发现错误只回到受影响路径修正，不以扩大架构代替解决具体问题。
4. 通过相应检查后递增SKILL.md的日期序号版本；同一发布中的相关修改可合成一个版本。API基线独立，未升级接口不改apiLevel基线。提交说明简述原因、变化、验证与限制；不为每次小修新增一份报告。
5. 保存技能并报告实际状态。公开发布再执行下方发布检查；技能保存成功不等于公开仓库同步成功。

## 按影响选择项目检查

|变化|必要检查|
|---|---|
|纯文字、标签、来源或链接|核对含义、链接和路由；确认没有意外改变执行约束；技能格式与差异检查|
|数值表/查询工具|受影响配置、锚点/插值/范围边界及调用者；工具有改动则实际运行；不把查询通过当硬件能力验证|
|动作、状态、模板或约束|检查规则→模板→审查是否一致；按回归维护表选择案例，核对理由，不仅比较类别/行号|
|修复实际漏检、误报或新增行为|尽量加入可复现最小案例及合法对照；已有案例完整覆盖时复用。暂不能构造时记录覆盖缺口，不能声称已回归验证|
|核心优先级、入口路由、跨维度状态或审查机制变动|做项目级一致性检查并运行完整现有回归；独立审查者不得读取答案或维护者诊断|
|API/安装基线升级|按upstream-maintenance.md核对来源、版本与兼容影响，再运行关联案例；不暗改现有客户协议|

项目级一致性检查关注：条目是否可达、触发条件是否明确、规则是否有唯一出处、重复/冲突/失效规则、模板是否覆盖核心规则、审查是否覆盖新增约束、资料及公开说明是否反映真实版本。出现同类偏差反复发生、跨章节冲突或准备批量发布时执行；没有具体变化时不例行重构。资料更新按需，不追随官方开发分支频繁同步。

## 公开发布与状态核对

- 区分“本地已修改”“技能已保存”“公开仓库已发布”；记录实际规则版本与对应提交号。默认可积累多个已保存版本后批量公开发布；用户明确要求推送时完成推送，不把本地提交当完成。
- 发布前读取远端当前分支头，与上次公开版本比较实际文件差异。保留仓库原有README、许可、第三方说明和他人改动；排除缓存、临时文件、认证信息及客户实验数据。案例应为去标识的最小片段，不直接公开客户完整协议。
- 更新中英文项目说明中的当前版本、实质变化、API基线变化与验证边界。历史报告保留原版本，不把旧测试结果改标为本次测试。版本展示可引用SKILL.md作为唯一当前规则依据，避免维护多套版本列表。
- 正常提交并推送，不强推。发布过程远端前进时，重新读取并合并相关差异，不覆盖新提交。推送后读取远端头和规则版本确认；只有核对一致才报告已发布，并给出提交链接。
- 格式错误、规则冲突、受影响案例失败或重要未决项未处理时，不标为验证通过。若仅因无执行环境而未测，明确检查范围；可保存待验证工作，但不能宣称稳定发布已验证。

## 回退与后续反馈

出现回归时，保留失败证据及影响版本，优先最小修复；需回退时用新提交撤销有问题的改动，保留历史和无关更新，再验证受影响范围。回退也使用新的规则版本并说明恢复的行为，不让相同版本对应不同内容。

实际反馈按“最小复现、预期/实际、规则/API/软件版本、适用配置”定位；新缺口先归入现有章节，只有确有独立职责且现有组织难以表达时才拆新文件。未覆盖项统一在回归维护说明中跟踪；报告可以引用，不再复制可变的待办清单。
